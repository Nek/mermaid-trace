# BASE-1: deterministic upstream SVG baselines

Status: implemented and verified on 2026-09-26. This is the first part of M1, not a mapped renderer.

As a renderer developer, I want reference SVG generated by pinned upstream Mermaid so changes to source metadata can later be checked without accepting accidental rendering changes.

## Scope and contract

Use Mermaid 12.0.0, Playwright 1.63.0 with its bundled Chromium, and Noto Sans 5.3.0 from Fontsource. Start with a few attributed flowchart inputs from Mermaid commit `98a0945418c76238f15df2afaddbba4272656c3b`, plus a project fixture for repeated labels. Pin configuration, viewport, locale, timezone, font and diagram IDs. Each diagram uses a fresh page; repeated passes launch fresh browser processes. Fonts load before rendering. Block external network access.

Compare exact SVG strings; no normalization initially. Discover and document any nondeterminism before changing comparison rules. Repeatability is scoped to the recorded rendering environment; cross-platform equality is not assumed. These are upstream reference artifacts, not source-mapped output or standalone font-packaged exports.

## Plan

1. Add a real rendering integration test before the generator: repeated render equality, existing-baseline comparison, invalid-input rejection. Confirm a failing run.
2. Install the three exact development dependencies and bundled Chromium. Add the smallest reusable reference-render helper and explicit baseline update command; no public renderer API or viewer.
3. Run the same render path in tests and generation. Inspect differences, generate and review the reference SVG, then prove ordinary tests detect a deliberately changed baseline without overwriting it.
4. Verify types/build/tests and frozen install; record limitations, update roadmap and commands, commit the coherent slice.

Future mapping tests will compare annotated output after removing only our metadata to these unchanged references, and independently assert source/AST mappings. Those tests, parser instrumentation, Markdown integration, Rust, and wider diagram coverage remain separate stories.

## Fixture provenance

The first three `.mmd` files in [the fixture directory](../../../mermaid-trace-ts/test/fixtures/flowchart) contain diagram strings copied from [Mermaid flowchart parser tests at commit 98a0945](https://github.com/mermaid-js/mermaid/blob/98a0945418c76238f15df2afaddbba4272656c3b/packages/mermaid/src/diagrams/flowchart/parser/flow.spec.js), the commit tagged `mermaid@12.0.0`:

| Fixture | Upstream test / adaptation |
|---|---|
| `whitespace.mmd` | `should handle a trailing whitespaces after statements`; decoded original string, including comments and whitespace, supplied directly to the renderer |
| `keywords.mmd` | `should handle node names with "end" substring`; original diagram string |
| `decisions.mmd` | `should add accTitle and accDescr to flow chart`; original template string including indentation |
| `repeated-labels.mmd` | Project-authored: repeated node/edge labels, nested groups, and Latin Unicode glyphs |

The [MIT notice](../../../mermaid-trace-ts/test/fixtures/flowchart/LICENSE) is retained with the copied inputs. Font binaries come from the locked Fontsource package and are loaded into the test page, not copied into the reference SVG.

## Verification and limits

- Red: test failed before the helper existed, then failed on missing expected SVG after implementation.
- Green: four fixtures rendered identically in three fresh browser processes, with the middle pass reversing input order. The test repeats these comparisons against saved SVG. No normalization was necessary.
- Node test runner: two passing integration tests (raw SVG baseline/determinism and explicit Mermaid parse-error rejection). Fonts must finish loading; attempted external requests are blocked and fail successful render passes.
- A deliberate change to an expected SVG caused the comparison to fail and remained untouched by the test; the original was restored afterward.
- Generated SVG parsed as XML and was visually reviewed in Chromium with the packaged font: 13 nodes and 10 edges across the corpus. Typecheck/build and frozen dependency installation were verified.
- Canonical environment: macOS ARM64, Chromium `153.0.8010.12`, with exact versions/configuration/font hash in [environment.json](../../../mermaid-trace-ts/test/baselines/environment.json). No cross-platform equivalence claim. The font is the Latin 400 subset; additional scripts/weights need explicit fixtures and font coverage.
- Fresh pages isolate Mermaid state for each diagram. The harness does not claim upstream Mermaid is deterministic under arbitrary page state, font fallback, configuration, or diagram types.
- Read [Mermaid configuration](https://mermaid.js.org/config/schema-docs/config.html) and [Playwright browser installation](https://playwright.dev/docs/browsers) when reviewing renderer upgrades. Baseline updates are explicit and never part of normal tests.
